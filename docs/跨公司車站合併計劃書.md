## 2. 實測發現（全部來自 `public/data/` 真實離線資料，2026-10-09）

### 2.1 ⚠️ 方向字母相反 —— 最容易漏掉的陷阱

同一個物理站，同一條路線，兩家的方向字母**相反**：

| 路線 | 九巴 | 城巴 | 維景酒店實際服務 |
|---|---|---|---|
| 103 | `I`→竹園邨　`O`→蒲飛路 | `O`→竹園　`I`→蒲飛路 | 九巴 `I` / 城巴 `O`（**都是往竹園**）|
| 113 | `I`→彩虹　`O`→堅尼地城 | `O`→彩虹　`I`→堅尼地城 | 九巴 `I` / 城巴 `O`（同樣相反）|

若按 `(route, dir)` 直接合併，會顯示成 `103 I`（九巴）與 `103 O`（城巴）**兩行**，用戶會誤以為是兩條不同路線。

### 2.2 ⚠️ 無全域規律，必須逐條預計算

在 43 條經確認屬同一走廊的路線中：

- **17 條**字母相反（KMB-`O` 對應 CTB-`I`）
- **26 條**字母相同

→ **無法**用「九巴恆等於城巴」或「恆相反」概括。方向對應表必須 build 時逐條算，runtime 不可推導。

### 2.3 ⚠️ 149 個共用路線號中，55 個是「撞號」

| 類別 | 數量 | 例子 |
|---|---|---|
| 真實同一走廊 | 94（63%）| 103：九巴 `I`→竹園邨／城巴 `O`→竹園 |
| **撞號（完全唔相干）** | **55（37%）** | 路線 1：九巴→尖沙咀碼頭／城巴→中環(港澳碼頭)，站序重疊 0.00 |

→ 單靠「路線號相同」判斷同一走廊會出大錯，必須用全線站序比對。

### 2.4 站名格式差異是系統性的

| | 用「,」逗號格式命名 |
|---|---|
| 城巴 | **2,267 / 2,587（88%）**（如「林士街, 德輔道中」）|
| 九巴 | 107 / 6,752（2%）|

→ 比對前必須剝除逗號後綴（`groupKey()` 已有此邏輯，需延伸）。另九巴站名帶分站編碼 `(KC334)`，城巴沒有。

### 2.5 純距離配對不可靠（實測準確率）

以「正規化站名是否相同」為指標：

| 距離 | 配對數 | 準確率 |
|---|---|---|
| 0–20m | 1,421 | 66% |
| 20–30m | 307 | 59% |
| 30–50m | 270 | 57% |
| 50–80m | 110 | **41%** |
| 80–120m | 86 | **15%** |
| 120m+ | 393 | ≤7% |

最離譜的誤配：6.6 公里外的「深圳灣口岸 ↔ 天恆邨總站 (TN971)」。

### 2.6 覆蓋率 vs 精確度取捨（實測）

| 準則 | 覆蓋城巴站 | 評估 |
|---|---|---|
| ≤50m 且站名不拘 | 1,065（41%）| 過嚴，漏掉「跑馬地馬場」等真實站 |
| **≤80m 且站名不拘** | **1,139（44%）** | **✅ 已選** |
| ≤80m 且站名相同 | 779（30%）| 過保守，七成站不合併 |
| ≤120m 且站名相同 | 785（30%）| 幾乎沒比 80m 多，不值 |

50m 之所以漏掉真實站：兩家巴士公司在同一橫街的**行車位分散**（例：城巴「跑馬地馬場, 摩理臣山道」距九巴「跑馬地馬場」54m 但確是同一站）。

## 4. 演算法設計

### 4.1 站名正規化（共用現有概念）

```
rawName → 剝除尾部 (CODE) 分站編碼 → 剝除「,」及其後綴 → trim
例：「九龍維景酒店 (KC334)」→「九龍維景酒店」
    「林士街, 德輔道中」→「林士街」
```

### 4.2 站點配對（build 時）

```
對每個城巴站 C：
  1. 取 C 的路線號集合 S_C
  2. 網格化查詢 150m 內的九巴站候選（cell ≈ 66m，檢查 3×3 鄰域）
  3. 對每個候選 K：計算共用路線號數 |S_C ∩ S_K|
  4. 評分：score = 共用數 × 1000 + (站名相同 ? 500 : 0) − 距離
  5. 取 score 最高且距離 ≤80m 者 → 建立配對 K ↔ C
  6. 一個 K 可對應多個 C（一對多，實測 53 組）
```

**關鍵**：距離門檻放寬到 80m 需配合「共用路線號」條件，兩者缺一不可。

### 4.3 方向對應（build 時）

```
對每個兩家都有的路線號 R：
  1. 取 KMB 與 CTB 該路線號的所有變體（dir × svc）
  2. 以正規化站名集合計 Jaccard 相似度
  3. 分類：
     · 最佳 Jaccard < 0.2 → 撞號，不建立對應
     · 最佳 Jaccard ≥ 0.5 → 同一走廊，記錄 (KMB_dir ↔ CTB_dir) 及信度
  4. 輸出 dirMap: { route → { kmbDir, ctbDir, score } }
```

實測結果：149 個路線號 → 55 撞號排除、43 確認同走廊、其餘信度不足不合併。

### 4.4 資料結構

併入 `ctb-routes.json.gz`（保持決定性）：

```js
{
  v: 1,
  routes,      // 既有：814 方向
  routeStops,  // 既有：17,404 筆
  cross: {
    stops: [[ctbId, [kmbId, ...]], ...],   // 站點配對（約 1,139 筆，一對多用陣列）
    dirs:  { "103": { k: "I", c: "O", s: 0.82 }, ... }  // 方向對應（約 43 筆）
  }
}
```

估計 gz 後約 +10 KB（站點配對表未 gz 前 64 KB → 給寬鬆估 12–15 KB）。

## 5. 實作步驟

### Phase 0 — `build-data.mjs`：加配對計算
1. 加 `normalizeStopName()`（剝 `(CODE)` + 剝逗號後綴）
2. 改 `buildKmb()` / `buildCtb()` 回傳中間資料（站點 `{id, name, lat, lng, routes:Set}`）供配對用
3. 實作 `computeStopPairs()`（網格化，8ms）
4. 實作 `computeDirMap()`（Jaccard）
5. 併入 `ctb-routes.json.gz` 的 `cross` 欄位
6. **連跑兩次驗證 buildId 相同**（決定性鐵律）
7. 印出統計：配對數、一對多組數、撞號數、確認同走廊數

### Phase 1 — `data.js`：合併查詢層
1. `loadStatic('ctb')` 讀入 `cross` → 建 `crossStops`（雙向 Map）與 `crossDirs`
2. 新增 `getMergedStopRoutes(store, stopId)` → 回 `{co, stopId, route, dir, dirKey}` 陣列，其中 `dirKey` 是**正規化方向鍵**（用 `dirMap` 把 CTB dir 映射到 KMB dir 空間）
3. `resolveRouteSeq` 支援跨公司：查 `crossDirs` 得知對應方向

### Phase 2 — `app.js`：同時載入 + 合併顯示
1. `boot()` 改為同時載入兩家（`Promise.all`），保留 `bootGen` race guard
2. 切換器改為「偏好」：只影響搜尋時 nearby 排序與預設公司標籤，**不再重載資料**
3. `renderNearby()`：合併分組 —— 先按 `crossStops` 併同公司站，再按 `groupKey()` 併同名站
4. `fetchEta()`：對合併後的 ids 陣列全部查（每個 id 用其 adapter），合併結果
5. `renderEta()`：按 `dirKey` 而非 `dir` 分組；每行加公司色點
6. 路線頁：跨公司路線的方向分頁需用 `dirMap` 對齊

### Phase 3 — `index.html` / `app.css`
1. 公司色點（`.co-dot`，6px 圓點，九巴紅／城巴黃）
2. 切換器標籤改為「優先顯示」
3. 合併站可加標籤（如「兩家公司」）

### Phase 4 — `sw.js`
- `SHELL` 已有兩家 gz，**無需改**（M8 已加）
- 確認 `bump-sw.mjs` 已跑

### Phase 5 — `verify.mjs`
新增分組 `[XCO-1]`~`[XCO-8]`：
- `[XCO-1]` build 產出 `cross.stops` 數量合理（>1,000）、`cross.dirs` 有 103/113
- `[XCO-2]` 維景酒店合併為一項、路線總數 = 16
- `[XCO-3]` `103` 只顯示**一行**（九巴 I + 城巴 O 合併）
- `[XCO-4]` 撞號路線（1、2、6）**不會**被合併
- `[XCO-5]` 一對多站（如牛頭角上邨）合併為一項
- `[XCO-6]` 兩家同時載入 <150ms
- `[XCO-7]` 連跑兩次 build buildId 相同（決定性）
- `[XCO-8]` 未配對站（1,436 個）行為不變

## 8. 與 M8 切換器的關係

M8 建立的切換器**保留但降級為「偏好」**：

| | M8 現況 | M9 目標 |
|---|---|---|
| 切換行為 | 重載另一家 gz（0.5–2s）| 僅改 localStorage 偏好，**零重載** |
| 用途 | 決定載入邊家 | 決定搜尋結果 nearby 排序、預設公司標籤 |
| 資料 | 只載一家 | 兩家都載 |

**為何保留**：用戶可能只想睇一家（減少畫面噪音），所以提供偏好而非強制全顯示。
